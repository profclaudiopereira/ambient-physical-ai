# Purpose

This Technical Note documents the engineering work that transformed the Echo Pyramid Voice Node into the local voice-input interface of the Ambient Physical AI ecosystem.

The implemented solution allows authenticated users to change the active environment context through offline speech recognition while preserving the Cognitive Runtime as the single authority responsible for semantic reasoning and context management.

This document records:

- architectural decisions;
- firmware implementation;
- ESP-SR integration;
- runtime integration;
- validated communication contracts;
- engineering rationale;
- validation evidence.

The implementation described here represents the first validated bidirectional voice interaction milestone of the Expression Layer.

---

# Engineering Goal

The objective of this work was to introduce local voice interaction without modifying the existing authentication architecture.

The validated interaction flow is:

```text

        ▼

        │
        ▼
User says:

        ▼

        │

        ▼

        │
        ▼

        ▼

        │
        ▼
Canonical Context Update
        │

        ▼

```

The implementation intentionally preserves NFC authentication.

Voice commands modify only the active environment context.

Responsibilities:

Validated wake phrase:


Validated behavior:

```text

↓

```

Representative execution flow:

```text

↓

↓

↓

```

The Wake Word does not trigger any communication with the Cognitive Runtime.

Its only purpose is to enable temporary command recognition.

# Context Change Requests

After a valid command is recognized, the firmware constructs a compact JSON request.

Example:

```json
{
  "type": "context_change_request",
  "requested_context": "Lab",
  "source": "voice_pyramid"
}
```

The request is transmitted through UDP to the Cognitive Runtime.

The Echo Pyramid does not validate:

- authenticated identity;
- authorization;
- session state;
- semantic consistency.

Those responsibilities remain exclusively inside the AX630C Cognitive Runtime.

# Command Window Timeout

During validation, one usability issue was identified.

When the command recognition window expired without a recognized command, the LED could remain in the listening state.

The final implementation handles the timeout explicitly.

```text
Command Timeout

↓

Recognition Window Closed

↓

No UDP Request

↓

Ready State Restored
```

This behavior prevents the device from appearing permanently stuck in listening mode and improves user experience during repeated interactions.

# ESP-SR Integration

The Echo Pyramid Voice Node uses the ESP-SR framework to provide local, offline speech recognition.

The speech pipeline combines:

- Audio Front-End (AFE);
- WakeNet;
- MultiNet.

The resulting architecture enables low-latency local recognition without requiring network connectivity during command detection.

```text
Microphones
        │
        ▼
Audio Front-End
        │
        ▼
WakeNet
        │
        ▼
MultiNet
        │
        ▼
Context Command Callback
```

The implementation intentionally separates speech recognition from Cognitive Runtime communication.

---

# Flash Configuration

During development it was confirmed that the physical hardware provides **8 MB of Flash memory**.

The initial firmware configuration behaved as though a significantly smaller Flash device were present, preventing correct deployment of ESP-SR speech models.

The project configuration was updated to use the actual Flash capacity.

This change allows:

- larger application images;
- dedicated speech-model storage;
- reliable ESP-SR deployment.

---

# Partition Table

A custom partition layout was adopted to support embedded speech models.

Conceptually:

```text
NVS

↓

↓
```

The dedicated model partition prevents overlap between firmware and speech models while simplifying deployment.

# PSRAM Utilization

WakeNet, MultiNet and the Audio Front-End require significantly more memory than the initial firmware baseline.

To accommodate these requirements, PSRAM support was enabled.

The Audio Front-End allocates large processing buffers using PSRAM whenever possible.

Benefits include:

- reduced internal RAM pressure;
- larger speech models;
- more stable runtime behavior;
- improved audio processing capacity.

# Cognitive Runtime Integration

The AX630C Cognitive Runtime was extended to process voice-originated context changes while preserving the active authenticated identity.

Responsibilities include:

- request validation;
- identity preservation;
- canonical context update;
- semantic event generation;
- event distribution.

The runtime continues listening for incoming requests using the validated UDP communication interface.

---

# Identity Preservation

A context-change request never replaces the authenticated user.

Instead:

```text
Authenticated User

↓

Context Change Request

↓

Context Validation

↓

Context Update

↓

Identity Preserved
```

The following information remains unchanged:

- authenticated user;
- user role;
- authorization;
- NFC identity;
- active session.

Only context-related fields are updated.

---

# Dedicated Semantic Event

Voice requests generate a dedicated semantic event.

```text
context_changed
```

This event is intentionally independent from:

```text
identity_authenticated
```

Reasons include:

- preserving semantic clarity;
- avoiding duplicated authentication behavior;
- preventing repeated welcome messages;
- allowing downstream nodes to distinguish between authentication and context transitions.

---

# Interpretation of Validation Results

Successful delivery of a UDP packet confirms that the Cognitive Runtime transmitted the semantic event.

It does **not** automatically confirm that downstream nodes:

- parsed the event;
- implemented the corresponding behavior;
- produced the expected physical response.

Consequently, two distinct validation levels must always be considered.

## Runtime Validation

```text
Event Generated

↓

Event Sent
```

---

## Device Validation

```text
Event Received

↓

Event Interpreted

↓

Physical Action Executed
```

Maintaining this distinction is important when validating distributed embedded systems.

# Known Limitations

The following observations were identified during engineering validation.

## Wake Word Sensitivity

Wake Word recognition became less sensitive after the complete WakeNet + MultiNet integration than during the earlier WakeNet-only experiments.

This behavior requires additional investigation involving:

- Voice Activity Detection (VAD);
- microphone gain;
- acoustic conditions;
- WakeNet sensitivity parameters;
- command window timing.

No retuning was performed during this milestone.

---

## Command Confidence

Different context commands were recognized with different confidence levels.

The current firmware accepts valid recognized commands regardless of confidence threshold.

Future work may investigate:

- minimum confidence policies;
- retry strategies;
- confirmation prompts;
- ambiguous command handling.

---

## Downstream Context Interpretation

The Cognitive Runtime successfully propagates the `context_changed` semantic event.

At the time of this validation, downstream firmware still required complete physical verification of their interpretation of the new event.

Examples include:

- Ambient Runtime visual updates;
- RGB lighting policies;
- additional Expression Layer reactions.

These items do not affect the correctness of the Echo Pyramid implementation.

# Engineering Decisions to Preserve

The following architectural decisions are fundamental to the current implementation.

1. NFC authentication remains the responsibility of the Identity Node.

2. The Echo Pyramid Voice Node never owns user identity.

3. The AX630C Cognitive Runtime remains the authoritative source for context.

4. Voice commands use canonical context names.

5. `context_changed` remains independent from `identity_authenticated`.

6. Context changes must not trigger a second authentication sequence.

7. Runtime communication continues to rely on validated communication contracts.

8. Hardware abstraction remains isolated through dedicated software components.

These principles shall be preserved during future firmware evolution.
