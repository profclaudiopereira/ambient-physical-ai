# 1. Purpose

This note records the engineering work completed to enable the Echo Pyramid to act as a local voice-input node for the Ambient Physical AI ecosystem.

The implemented journey is:

```text
User authenticates through M5Dial/NFC
        ↓
AX630C stores the active identity and initial context
        ↓
User says the Wake Word: "Hi ESP"
        ↓
Echo Pyramid opens a context-command recognition window
        ↓
User says one canonical context:
Research / Lab / Meeting / Classroom / Demo
        ↓
Echo Pyramid sends a context_change_request by UDP
        ↓
AX630C preserves the active identity
        ↓
AX630C updates the canonical context
        ↓
AX630C generates context_changed
        ↓
Semantic Dispatcher propagates the event
        ↓
Ambient Runtime and Expression nodes receive the update
```

This work does not replace NFC identity. The voice input changes only the active environment context.

# 2. Architectural Decision

The responsibilities are intentionally separated.

## 2.1 M5Dial / Identity Node

Responsible for:

- identifying the person through NFC;
- resolving the user profile;
- selecting the initial context;
- sending the canonical `identity_package`;
- establishing the active identity in the AX630C runtime.

## 2.2 Echo Pyramid

Responsible for:

- detecting the local Wake Word;
- recognizing one of the predefined context commands;
- sending a context-change request;
- providing immediate local LED feedback;
- reproducing personalized TTS audio generated by the AX630C.

The Echo Pyramid is **not** the context authority.

## 2.3 AX630C Cognitive Runtime

Responsible for:

- storing the active identity;
- validating context-change requests;
- preserving identity, role, authorization, NFC UID and session state;
- updating the canonical runtime context;
- generating normalized semantic events;
- dispatching updates to the Ambient Runtime and Expression Layer.

The AX630C remains the system authority for context.

# 4. Firmware Work Completed

## 4.1 Wake Word

The firmware uses ESP-SR WakeNet with the English wake phrase:

```text
Hi ESP
```

Configured WakeNet model:

```text
wn9_hiesp
```

Validated behavior:

```text
Idle
  ↓
"Hi ESP" detected
  ↓
Context command recognition window opens
  ↓
LED changes to blue
```

Representative firmware log:

```text
WAKE WORD DETECTED | word=1 | model=1 | channel=0
Context command window OPEN | Research/Lab/Meeting/Classroom/Demo
Wake Word callback | phrase=Hi ESP | word=1 | model=1
Expression action: RGB_BLUE
```

## 4.2 Local command recognition

ESP-SR MultiNet is used for offline recognition of the canonical context set:

```text
Research
Lab
Meeting
Classroom
Demo
```

Configured model:

```text
MultiNet6 English quantized
```

The canonical words intentionally match the values already used by:

- M5Dial context selection;
- AX630C Context Package;
- Ambient Runtime;
- semantic events;
- project documentation.

No translation or aliasing layer is currently required.

## 4.3 Context-command behavior

After the Wake Word, the firmware opens a temporary recognition window.

On a valid command:

```text
Recognized command
        ↓
Build JSON request
        ↓
Send UDP to AX630C
        ↓
LED changes to green
```

Example:

```json
{
  "type": "context_change_request",
  "requested_context": "Lab",
  "source": "voice_pyramid"
}
```

Destination:

```text
192.168.77.202:4444
```

Representative log:

```text
CONTEXT COMMAND DETECTED | id=5 | prob=0.219
Voice context selected | context=Demo | probability=0.219
Context change request sent | context=Demo | target=192.168.77.202:4444
Payload: {"type":"context_change_request","requested_context":"Demo","source":"voice_pyramid"}
Expression action: RGB_GREEN
```

## 4.4 LED semantics

The current firmware uses the following immediate local feedback:

```text
Blue  = Wake Word accepted; command window open
Green = Request sent successfully or local timeout handled
Red   = Request/send failure
```

The LED behavior is local feedback only. It does not replace the Cognitive Runtime State indicator.

## 4.5 Command-window timeout correction

During validation, the command window could expire while the LEDs remained blue.

The implemented correction handles MultiNet command ID `0` as a local timeout:

```text
Command ID 0
        ↓
No UDP request is sent
        ↓
LED leaves blue state
        ↓
Node returns to ready/green state
```

This avoids leaving the device visually stuck in a listening state.

# 5. ESP-SR and ESP-IDF Configuration

## 5.1 Flash-size correction

The physical device has 8 MB flash, but the project initially behaved as if only 2 MB were available.

This caused application and speech-model partition problems.

The firmware configuration was corrected to use the real 8 MB flash capacity.

## 5.2 Custom partition table

A custom `partitions.csv` was introduced:

```csv
# ESP-IDF Partition Table
# Name,     Type, SubType, Offset,   Size,    Flags
nvs,        data, nvs,     0x9000,   24K,
phy_init,   data, phy,     0xf000,   4K,
factory,    app,  factory, 0x10000,  1536K,
model,      data, spiffs,  ,         6000K,
```

Purpose:

- preserve sufficient application space;
- allocate a large dedicated model partition;
- allow ESP-SR model packaging;
- fit WakeNet and MultiNet models in flash;
- avoid application/model overlap.

## 5.3 PSRAM

PSRAM was enabled through `idf.py menuconfig`.

The AFE memory strategy uses:

```c
AFE_MEMORY_ALLOC_MORE_PSRAM
```

This was necessary because WakeNet, MultiNet, audio front-end processing and model buffers exhausted internal memory when combined.

## 5.4 WakeNet selection

Relevant configuration:

```text
WakeNet model: wn9_hiesp
Wake phrase: Hi ESP
```

## 5.5 MultiNet selection

Relevant configuration:

```text
CONFIG_SR_MN_EN_MULTINET6_QUANT=y
```

This enables the quantized English MultiNet6 model.

## 5.6 Audio front end

The audio path uses the AFE with microphone and reference channels.

The reference channel is important for Echo Pyramid audio behavior because the device also reproduces sound.

The integration uses a multi-rate/multi-channel AFE configuration compatible with WakeNet and MultiNet.

## 5.7 VAD observation

During MultiNet integration, Wake Word sensitivity appeared lower than in the earlier WakeNet-only validation.

One relevant difference observed in the configuration was:

```c
config->vad_init = true;
```

where the previous WakeNet-only baseline used:

```c
config->vad_init = false;
```

No sensitivity tuning was performed in this closing session.

This remains an explicit next-session task.

# 6. Windows Build Environment Requirements

The ESP-SR model packaging tool produced Windows encoding failures under the default `cp1252` environment.

Before ESP-SR builds, the following commands were required in Windows CMD:

```cmd
set PYTHONUTF8=1
set PYTHONIOENCODING=utf-8
chcp 65001
```

These settings prevent Unicode failures in ESP-SR tooling, especially in:

```text
movemodel.py
```

Recommended build sequence:

```cmd
set PYTHONUTF8=1
set PYTHONIOENCODING=utf-8
chcp 65001

idf.py fullclean
idf.py build
idf.py flash monitor
```

These environment settings are build-session settings. They must be reapplied in a new CMD session unless made persistent by the developer.

## 8.2 Identity preservation

A context-change request does not replace the active identity.

Example before voice command:

```json
{
  "who": {
    "id": "mariana",
    "name": "Mariana",
    "role": "researcher",
    "identity_source": "nfc",
    "uid": "8804D225"

    "environment": "Classroom",
    "location_source": "identity_context"
  }

```

Example after voice command:

```json
{
  "who": {
    "id": "mariana",
    "name": "Mariana",
    "role": "researcher",
    "identity_source": "nfc",
    "uid": "8804D225"
  },
  "where": {
```

Preserved fields include:

- user ID;

Changed fields include:

- `where.environment`;
- `where.location_source`;
- `what.activity`;
- `what.event_type`;
- `why.intent`;
- `why.reasoning`;
- `source.context_change_source`.

## 8.3 Valid contexts

The AX630C validates requests against:

```text
Research
Lab
Meeting
Classroom
Demo
```

Invalid names are rejected.

A context-change request is also rejected if no active authenticated identity exists.

## 8.4 Dedicated semantic event

A new event was introduced:

```text
context_changed
```

This event is intentionally separate from:

```text
identity_authenticated
```

Reason:

- avoid a second welcome message;
- avoid replaying authentication effects;
- preserve semantic clarity;
- allow downstream nodes to react specifically to environment changes.

Example:

```json
{
  "schema_version": "1.0",
  "type": "semantic_event",
  "event_type": "context_changed",
  "target": "cognitive_runtime",
  "priority": "high",
  "payload": {
    "user_id": "mariana",
    "user_name": "Mariana",
    "source_role": "researcher",
    "role": "researcher",
    "access_level": "full_research",
    "capabilities": [
      "ambient_runtime",
      "expression_layer",
      "research_equipment",
      "cognitive_runtime",
      "administration"
    ],
    "previous_context": "Classroom",
    "environment": "Lab",
    "activity": "context_change",
    "state": "validated",
    "request_source": "voice_pyramid"
  }
}
```

# 12. Important Interpretation of Delivery Logs

A line such as:

```text
RGB expression semantic event sent to 192.168.77.205:5555
```

confirms that the AX630C successfully submitted the UDP datagram.

It does not, by itself, prove that the destination firmware:

- received the packet;
- parsed `context_changed`;
- mapped `Lab` to a lighting policy;
- applied a physical LED change.

Final physical validation requires logs or visible behavior from the destination node.

The same principle applies to the Tab5.

# 13. Known Limitations and Pending Work

## 13.1 Wake Word sensitivity

After MultiNet integration, Wake Word sensitivity appeared lower than during the WakeNet-only test.

Items to investigate:

- `vad_init`;
- AFE VAD behavior;
- microphone gain;
- noise suppression;
- WakeNet threshold;
- command-window timing;
- acoustic echo conditions;
- distance and direction from the microphone;
- accessible operation for users with softer speech or articulation differences.

This must be treated as an accessibility and usability requirement, not only as performance tuning.

## 13.2 Command confidence

Some commands were detected with high confidence, for example:

```text
Meeting probability: 0.995
```

Other valid recognitions occurred with lower probability, for example:

```text
Demo probability: 0.219
```

The current behavior accepts the detected command.

A later policy may define:

- minimum confidence;
- retry behavior;
- audio confirmation;
- ambiguous-command handling;
- accessible fallback interaction.

## 13.3 RGB context policies

The Cognitive Runtime now sends the required event and fields.

The RGB firmware must still be reviewed to confirm support for:

```text
context_changed
```

and define context-to-light mappings such as:

```text
Research  → focused neutral light
Lab       → bright technical light
Meeting   → balanced collaborative light
Classroom → clear instructional light
Demo      → presentation/demo lighting
```

These mappings must remain consistent with the project distinction:

- StickC Plus2 RGB Node: cognitive-state explanation;
- Atom Matrix and RGB Strip: physical environmental transformation.

## 13.4 Tab5 context reaction

The AX630C sends the new event to the Tab5.

The Tab5 firmware still needs final validation that it:

- parses the full event payload;
- updates the displayed active context;
- preserves local sensor information;
- does not confuse context update with identity authentication.

## 13.5 StackChan

The StackChan adapter prepares the notification, but physical delivery/reaction remains pending.

This does not block the Echo Pyramid context-change journey.

## 13.6 External personal context

The runtime logged:

```text
TMDB_BEARER_TOKEN is not configured
```

The failure is non-blocking.

It only prevents external profile-specific content that depends on TMDB.

# 16. Engineering Decisions to Preserve

The following decisions must not be changed casually:

1. The M5Dial remains the identity authority.
2. The Echo Pyramid does not redefine the active identity.
3. The AX630C remains the context authority.
4. Voice commands use canonical context values.
5. `context_changed` is distinct from `identity_authenticated`.
6. Context changes must not replay the welcome greeting.
7. Local Windows repository files are edited first.
8. Deployment to AX630C occurs through the repository BAT.
9. Existing validated UDP ports and IP assignments must be preserved.
10. Runtime delivery and physical-device interpretation remain separate validation layers.
11. Important functions, contracts, hardware assumptions and non-obvious decisions must remain documented in code.
12. Any future change must revalidate the complete NFC + voice + semantic journey.
