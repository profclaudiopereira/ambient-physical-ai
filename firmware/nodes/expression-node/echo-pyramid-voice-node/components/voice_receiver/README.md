# Voice Receiver

## Echo Pyramid Voice Node

### Expression Layer — TCP PCM Transport

The **Voice Receiver** is responsible for receiving PCM audio streams over TCP and forwarding validated audio blocks to the Echo Pyramid Voice Node application.

The component intentionally separates network transport from audio hardware implementation.

It does not access the Echo Pyramid codec, I²S peripheral, speaker driver or vendor library directly.

Instead, the application supplies a playback callback that owns the hardware-specific rendering process.

---

# Purpose

The Voice Receiver provides the incoming speech transport used by the Echo Pyramid Voice Node.

Its responsibilities are:

* start a dedicated TCP server;
* accept incoming voice connections;
* validate the voice transport contract;
* receive ordered PCM audio blocks;
* invoke the application-owned playback callback;
* isolate network transport from audio hardware.

The component performs no speech synthesis and no semantic processing.

Speech content is generated by the Cognitive Runtime before transmission.

---

The Voice Receiver only understands the transport contract.

The application remains responsible for reproducing the received PCM samples.

# Public API

The public interface is intentionally small.

Default listening port:

```c
#define VOICE_RECEIVER_DEFAULT_PORT 5006
```

The application starts the receiver using:

```c
esp_err_t voice_receiver_start(
    uint16_t port,
    voice_receiver_playback_cb_t playback_cb);
```

Parameters:

* `port`: TCP listening port;
* `playback_cb`: application-owned PCM playback callback.

The function returns `ESP_OK` when the receiver task is created successfully.

---

# Playback Callback

The Voice Receiver delegates PCM rendering to the application through the following callback contract:

```c
typedef esp_err_t (*voice_receiver_playback_cb_t)(
    const int16_t *samples,
    size_t sample_count);
```

The callback receives:

* a pointer to signed 16-bit PCM samples;
* the number of mono samples in the current block.

The callback is responsible for forwarding these samples to the local audio subsystem.

Conceptually:

```text
Voice Receiver

↓

PCM Block

↓

Application Callback

↓

Audio Bridge

↓

Speaker
```

This callback-based design prevents reverse coupling between the transport component and the Echo Pyramid hardware layer.

# APAI Voice Protocol V1

The Voice Receiver operates with the APAI Voice Protocol V1 used by the Cognitive Runtime.

Conceptual stream structure:

```text
Protocol Header

↓

PCM Payload
```

The header identifies and describes the incoming audio stream.

The payload contains the ordered signed 16-bit mono PCM samples.

The protocol allows the embedded node to validate the complete audio format before forwarding samples to the playback layer.

---

# Why TCP

TCP was selected for voice delivery because audio streams require:

* ordered delivery;
* reliable transmission;
* complete stream reconstruction;
* protection against missing or reordered blocks.

Using TCP avoids implementing custom UDP fragmentation, sequencing and retransmission logic inside the embedded node.

UDP remains appropriate for compact semantic commands, while TCP is reserved for ordered PCM transport.

```text
UDP

Semantic Commands
```

```text
TCP

Voice Audio
```

# Error Handling

The Voice Receiver validates required startup parameters.

Invalid conditions include:

* TCP port equal to zero;
* null playback callback;
* unsupported voice format;
* invalid protocol header;
* interrupted or incomplete stream;
* memory allocation failure;
* playback callback failure.

Transport errors must remain isolated from the rest of the firmware whenever possible.

A failed voice stream must not redefine system identity, context or semantic state.

---

# Integration with the Audio Bridge

The Voice Receiver does not depend directly on the Audio Bridge.

The integration is performed by the application.

```text
voice_receiver_start()

↓

Application registers callback

↓

Voice Receiver receives PCM

↓

Callback calls audio_bridge_play_pcm()
```

This approach keeps both components reusable.

The Voice Receiver owns transport.

The Audio Bridge owns hardware access.

---

# Integration with Wake Word Detection

The Voice Receiver and Wake Word Detector use the same physical audio subsystem for different directions.

```text
Voice Receiver

Incoming PCM Playback
```

```text
Wake Word Detector

Microphone Capture
```

The application coordinates both components.

Before reproducing received audio, the application may temporarily pause local speech recognition to prevent:

* self-triggering from the speaker;
* simultaneous capture and playback conflicts;
* stale recognition state after TTS playback.

This coordination remains outside the Voice Receiver.

# Design Decisions

## Transport and Playback Separation

The component receives PCM but never renders it directly.

This allows the audio hardware implementation to change without modifying the TCP transport.

---

## Callback-Based Integration

The application owns the playback callback.

This prevents the Voice Receiver from depending on application-specific hardware abstractions.

---

## Fixed V1 Audio Format

The first protocol version uses a fixed and validated audio format:

```text
16 kHz

Mono

Signed 16-bit PCM
```

A fixed format simplifies validation, buffering and embedded playback.

---

## Dedicated Runtime Task

The receiver operates as an independent task.

This prevents the main application loop from blocking while waiting for TCP clients or PCM data.

# Summary

The Voice Receiver provides a compact and reusable TCP PCM transport component for the Echo Pyramid Voice Node.

Its responsibilities are intentionally restricted to:

```text
TCP Reception

↓

Voice Stream Validation

↓

PCM Block Delivery

↓

Application Callback
```

By isolating network transport from audio hardware, the component preserves clear ownership boundaries and allows the Cognitive Runtime, transport layer and embedded audio implementation to evolve independently.
