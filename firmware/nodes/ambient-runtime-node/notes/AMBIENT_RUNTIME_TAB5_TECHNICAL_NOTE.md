## 2. Architectural Responsibility of the Tab5

The Tab5 is the Ambient Runtime Node of the Ambient Physical AI ecosystem.

Its current responsibilities are:

- monitor the local environmental hardware;
- maintain the Ambient Runtime operational console;
- report network and hardware status;
- receive Semantic Events addressed to the Ambient Runtime;
- expose the latest received Semantic Event in the local console;
- manage the content displayed on the Mini OLED connected through the PaHub.

The Tab5 does not orchestrate the Expression Layer.

Expression devices such as StackChan, Voice Pyramid, RGB nodes, and future expression nodes receive their own Semantic Events directly from the Semantic Dispatcher or Semantic Event Bus.

The architectural relationship remains:

```text
Cognitive Runtime
        ↓
Semantic Dispatcher
        ├── Ambient Runtime — Tab5
        ├── StackChan
        ├── Voice Pyramid
        ├── RGB / visual expression nodes
        └── Other expression nodes
```

## 3. Existing Tab5 Operational Console

The main 5-inch Tab5 display was already implemented before this integration step.

It presents the operational state of the Ambient Runtime, including:

- local environmental sensor values;
- I2C device status;
- PaHub status;
- network connectivity;
- IP address and RSSI;
- hardware readiness;
- cognitive/runtime connectivity state.

The main console design is considered complete.

It must not be redesigned as a personalized user interface.

User-dependent contextual information belongs to the Mini OLED, not to the main 5-inch console.

---

## 4. Semantic Event Receiver Integration

The Tab5 Semantic Event receiver was extended to preserve additional information from the most recently received event.

The receiver status now exposes:

```cpp
last_event_type
last_target
```

These values represent the latest valid Semantic Event received by the Ambient Runtime.

The status is updated atomically inside the receiver critical section so that the event type and target are always read as a consistent pair.

The receiver is intended to expose an operational snapshot.

It is not an event history or persistent event queue.

---

## 5. Propagation to the Ambient Console

The Ambient Runtime console data structure was extended with:

```cpp
char cognitive_event[64];
char cognitive_target[64];
```

The main application retrieves the current receiver snapshot and copies the values into the console data structure.

When no Semantic Event has been received, the console uses:

```text
none
```

as the fallback value.

The data path is currently:

```text
Semantic Event received through UDP
        ↓
Semantic Event Receiver
        ↓
Receiver operational snapshot
        ↓
main.cpp
        ↓
Ambient Console data
        ↓
Tab5 5-inch display
```

## 8. Event Text Truncation

The complete event identifier:

```text
identity_authenticated
```

does not currently fit in the available console rendering width.

The rendering code intentionally limits the amount of text written to the local formatting buffer in order to avoid the compiler error:

```text
-Werror=format-truncation
```

As a result, the current screen shows a truncated technical identifier.

Example:

```text
identity_authentica...
```

This does not affect event reception or processing.

It is currently a presentation issue only.

The final correction may use one of the following approaches:

- a shorter presentation label;
- a dedicated event-to-display-name mapping;
- adjusted rendering width;
- an alternate two-line presentation.

The internal canonical event identifier must remain unchanged for communication and logging.

## 9. Mini OLED Current State

The Mini OLED is connected to the Tab5 I2C bus through the PaHub.

Current sequence:

```text
PaHub OLED channel selection
        ↓
OLED initialization
        ↓
OLED clear
        ↓
Diagnostic text rendering
```

The current diagnostic message is:

```text
AI
RUN
TEST
```

This message has already been displayed correctly on the physical device on multiple occasions.

However, the rendering later became unstable and currently presents corrupted or unexpected pixels.

The following observations were established:

- the display has already operated correctly;
- the PaHub uses exclusive single-channel selection;
- ENV-IV and DLight transactions are not simultaneously routed to the OLED;
- the OLED is currently written during initialization;
- no confirmed concurrent display writer was identified;
- repeated diagnostic rendering did not consistently recover the correct image.

The driver therefore remains experimentally validated but not yet robust enough for final delivery.

The temporary diagnostic rewrite inside the main runtime loop must not remain in the final baseline.

Before committing, the loop should contain only the original PaHub channel verification unless a deliberate diagnostic commit is being created.

## 10. Intended Mini OLED Content

The Mini OLED is the portion of the Ambient Runtime intended to display contextual information.

It will present two categories of content.

### Common content

Information available to every authenticated profile:

```text
Local weather forecast
```

The forecast must correspond to the physical location of the room or environment.

### Profile-specific content

Examples already defined for the project:

```text
Claudio
└── exchange rate / US dollar information

Hermínio
└── Sport Club do Recife information

Mariana
└── cinema information
```

The Mini OLED content may change according to the authenticated profile, while the main 5-inch operational console remains unchanged.
